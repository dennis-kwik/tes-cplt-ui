# 20. Self-Audit Pass (WAJIB, langkah terakhir sebelum file dikirim)
Ditambahkan setelah ditemukan pola kegagalan berulang pada hasil produksi: kontradiksi antar sheet (mis. Message Catalog menyebut "N file PDF", Data_API menyebut "N file ATAU 1 ZIP" untuk topik yang sama), Component ID yang tidak konsisten skemanya, dan jumlah Test Scenario yang under-coverage tanpa disadari. Semua ini TIDAK ketemu di 1x proses generate pertama — baru ketemu kalau ada langkah baca-ulang eksplisit yang diarahkan untuk mencari masalah, bukan cuma menyelesaikan tabel demi tabel secara linear.

## 20.0 WAJIB MESKI MAHAL TOKEN (prinsip Goal-Driven Execution)
Evaluasi jujur terhadap hasil produksi nyata menemukan: aturan mekanis yang SUDAH eksplisit tertulis (freeze pane, lebar kolom seragam, Component ID konvensi) tetap tidak konsisten diterapkan di seluruh sheet — **punya aturan tidak sama dengan menegakkannya**. Ditarik kesimpulan: dorongan efisiensi token yang ditekankan di banyak bagian metodologi ini kemungkinan nyata **berkontribusi** ke kegagalan ini — verifikasi menyeluruh (cek ulang semua sheet, audit ulang semua ID) itu sendiri mahal token, dan tanpa penegasan eksplisit "langkah ini wajib meski mahal", ada risiko dilewati demi hemat.
**Aturan tegas**: Self-Audit Pass BUKAN langkah opsional yang boleh dipersingkat demi efisiensi token. Efisiensi token berlaku untuk cara MENULIS konten (ringkas, tidak bertele-tele), BUKAN untuk MELEWATKAN langkah verifikasi. Kalau Self-Audit Pass menemukan pelanggaran, perbaiki — jangan dibiarkan demi "sudah cukup panjang responsnya".

## 20.1 Kenapa ini perlu jadi langkah terpisah, bukan cuma "hati-hati saat menulis"
Saat generate 10-15 sheet sekaligus (Index_Summary, Snapshot, Redrawn, sheet spec per Desain UI, sheet lintas-modul), keputusan yang diambil di 1 sheet (mis. tafsiran default untuk ambiguitas requirement — lihat 3.3b) sangat mudah tidak ter-propagate konsisten ke sheet lain yang ditulis belakangan atau lebih dulu. Proses generate linear (tulis sheet 1, lalu sheet 2, dst) TIDAK otomatis mengecek balik konsistensi ke sheet yang sudah selesai duluan. Self-Audit Pass adalah langkah eksplisit untuk baca ulang SELURUH workbook sebagai satu kesatuan, bukan sheet-per-sheet dalam isolasi.

## 20.2 Prosedur — CHECKLIST TERCENTANG SATU-SATU (bukan baca sekilas lalu dianggap oke)
Setelah seluruh sheet selesai ditulis (tahap draft), sebelum file dianggap final, jawab EKSPLISIT ya/tidak untuk tiap poin — kalau ada yang "tidak", perbaiki dulu sebelum lanjut ke poin berikutnya:
- [ ] **Ambiguity consistency check**: semua topik yang ditandai punya >1 tafsiran (3.3b) — sudah dicek ke SEMUA sheet yang menyinggungnya (Business Rules, Field Matrix, Message Catalog, Data_API, Test Scenario), dan semuanya pakai tafsiran default yang SAMA?
- [ ] **Component ID schema check**: SEMUA Component ID di Field Matrix ikut pola `CMP-[FIELD]-[MODE]-[STATUS]` dengan token dari kosakata baku (7.3b) — tidak ada syarat kondisional bebas yang nyelip ke posisi Status?
- [ ] **Related ID & hyperlink check**: Related ID 1 di setiap baris yang punya relasi sudah diisi DAN di-hyperlink ke cell asal (7.3c)?
- [ ] **Test coverage math check**: hitung ulang jumlah Business Rule Critical dan jumlah Critical Challenge, dibandingkan ke formula 16.3 — apakah jumlah Test Scenario aktual >= hasil formula?
- [ ] **Format mekanis check**: freeze pane aktif di SEMUA sheet spec (bukan sebagian)? Lebar kolom seragam 2,57 di SEMUA sheet Redrawn (bukan sebagian)? Autofilter aktif di SEMUA tabel? Assumption fill kuning DAN Auto-Applied fill oranye diterapkan konsisten di semua baris yang relevan (bukan cuma sebagian baris)?
- [ ] **Devil's advocate terhadap hasil sendiri**: re-run persona Critical Challenge (14.4), target-nya WORKBOOK YANG BARU SELESAI DIBUAT, bukan requirement asli. Ada assumption yang ditulis seolah final (bukan "BELUM DIPUTUSKAN")? Ada rule yang bertentangan dengan rule lain di sheet yang sama atau sheet berbeda? Temuan Critical Challenge sudah dibawa balik memperbaiki Business Rules terkait (bukan cuma dicatat di sheet Challenge saja)?
- [ ] **Auto-apply propagation check**: semua kandidat Pola Teknis Standar/What-If Near+mitigasi konkret sudah benar-benar masuk ke Business Rule/Field Matrix/Test Scenario (14.4c) — bukan cuma tertulis di sheet What_If_Critical_Challenge saja?
- [ ] **Cross-check angka Index_Summary**: angka ringkasan (jumlah rule/component/test/dst) cocok dengan jumlah baris aktual di tiap sheet — bukan angka perkiraan yang ditulis sebelum sheet selesai?
- [ ] **Element inventory cross-check** (3.4d): inventaris muncul VISIBLE di sheet `_Snap` (bukan cuma langkah kerja internal)? Setiap elemen di inventaris ada di redraw? Teks SAMA PERSIS (verbatim) — tidak diparafrase/"dikoreksi"? Urutan & pengelompokan ikut Traversal Order (3.4c), bukan disusun ulang? Tidak ada elemen kecil/dekoratif yang hilang?
- [ ] **Depth Balance check** (3.4f): Narrative Spec Panel di `_Redr` TIDAK lebih detail dari sheet spec formal? Sheet spec formal minimal SETARA kedalamannya dengan narasi (tidak lebih dangkal)?
- [ ] **No-duplikasi Tools vs List View** (3.4e): trigger/icon yang sudah dijelaskan di section Tools/Trigger tidak diulang lagi di List View Kolom?
- [ ] **Urutan sheet check** (17.1): workbook dikelompokkan per JENIS (semua Snap → semua Redrawn → semua Spec Formal → lintas-modul) — bukan diulang per modul berselang-seling?
- [ ] **File integrity check** (22.5): file berhasil dibuka ulang tanpa error?

## 20.3 Kalau Self-Audit menemukan masalah
Perbaiki langsung sebelum file dikirim — Self-Audit Pass bukan langkah pelaporan pasif, tapi langkah korektif. Kalau suatu ketidakkonsistenan butuh keputusan bisnis yang tidak bisa diambil sendiri (bukan sekadar salah tulis), catat sebagai entry baru di `Assumption_Decision_Risk_Open` dan `What_If_Critical_Challenge`, jangan dibiarkan sebagai kontradiksi diam-diam.

## 20.4 Batasan yang jujur
Self-Audit Pass mengurangi risiko kontradiksi dan drift, tapi tidak menjamin nol kesalahan — ini tetap proses baca-ulang oleh agent yang sama, bukan verifikasi independen oleh pihak ketiga. Untuk requirement yang sangat kritis/high-stakes, tetap rekomendasikan review manusia (BA/PO/System Analyst) sebelum development dimulai, terutama untuk item yang statusnya masih Assumption/Open di `Assumption_Decision_Risk_Open`. **Direkomendasikan tambahan**: buka sesi/chat BARU (tanpa histori diskusi drafting) untuk melakukan cek independen kedua — sesi yang sama yang baru saja generate cenderung "percaya" hasilnya sendiri, sesi baru tanpa konteks drafting lebih mungkin menemukan gap yang terlewat.
